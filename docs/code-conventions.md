# Правила разработки QCanva

Этот документ — короткий контракт для нового кода. Он закрепляет границы,
которые появились после рефакторинга Canvas, Dashboard и общей UI-библиотеки.
Если изменение требует обходить правило, сначала обновите архитектурное описание
и добавьте тест на новый контракт.

## Границы кода

- `src/views/` управляет маршрутом, загрузкой страницы и композицией секций.
  Повторяющаяся разметка, меню, карточки, диалоги и toolbar живут в
  `src/components/`.
- `src/components/dashboard/` содержит dashboard-секции и их локальный UI.
  API-запросы находятся в `src/api/`, жизненный цикл загрузки и ошибок — в
  composable рядом с ним или в компоненте секции.
- `src/components/ui/` содержит только повторяющийся application chrome:
  кнопки, поля, модалки, меню, пустые состояния и переключатели. Компонент
  становится общим после двух реальных потребителей; resource-specific карточки
  и canvas-инструменты в эту папку не выносятся.
- Один компонент отвечает за один участок поведения. Если экран начинает
  передавать десятки обработчиков и состояний в дочерний компонент, сначала
  вынесите секцию или composable, а не добавляйте ещё один проп.

## Vue и TypeScript

- Для новых компонентов используйте `script setup`, типизированные `defineProps`
  и `defineEmits`. Состояние передаётся вниз через props, изменения — вверх
  через события; не мутируйте prop и не меняйте состояние родителя напрямую.
- API компонента должен быть маленьким и явным. Для контролируемых значений
  используйте `modelValue` и `update:modelValue`; для действий — именованные
  события (`close`, `select`, `retry`, `changed`).
- `ref` на дочерний компонент допускается только для короткого императивного
  API. Такой API объявляется через `defineExpose`, не через доступ к внутренним
  DOM-узлам и не через поиск элементов по глобальному селектору.
- `UiMenu` владеет открытой панелью, Teleport для sheet-режима, ролью панели и
  остановкой клика. Dashboard-меню передаёт только trigger, содержимое и
  доменные `data-*` hooks; собственные Teleport-блоки в таких потребителях не
  дублируются.
- `UiSegmentedControl` владеет `aria-pressed`, активным состоянием и событием
  `update:modelValue`. Старые селекторы можно передать через typed option attrs,
  чтобы миграция сохраняла пользовательские и тестовые hooks.
- Общее состояние страницы хранится в composable или в родительской секции.
  Компонент отображения не должен сам решать, какой маршрут открыть: он
  сообщает о действии событием.
- `SharedSidebarShell` владеет только внешней оболочкой sidebar: `aside`,
  mobile-backdrop, Escape и focus trap. AppSidebar и DashboardSidebar передают
  header/content/footer слотами и сохраняют свои доменные классы, дерево и
  навигационные события внутри.
- Action-компоненты документов (`TextDocumentMobileMenu` и следующие UI-срезы)
  владеют своим Teleport, backdrop и стабильными DOM hooks. `TextDocumentView`
  хранит состояние и бизнес-обработчики, связывая их с компонентом через
  typed events.
- Для иконок используйте Lucide или существующую иконку проекта. Эмодзи и
  inline-иконки с разными стилями для одинаковых действий не добавляйте.

## CSS и дизайн-токены

- `src/style.css` — только global entrypoint с импортами. Новое глобальное
  правило добавляется в самый узкий модуль `src/styles/`, а не в монолит и не
  в конец entrypoint. Component-only CSS держите в `<style scoped>` компонента.
- Имя нового модуля сохраняет числовой порядок и домен, например
  `18-dashboard-spaces.css`. После добавления обновите
  [`src/styles/README.md`](../src/styles/README.md).
- Цвета, поверхности, границы, тени, радиусы и focus-состояния берите из
  токенов `src/styles/01-global.css`. Не вводите новый raw `rgba`, hex или
  отдельный breakpoint, если подходящий токен уже существует.
- Порядок импортов в `src/style.css` является частью поведения каскада. При
  переносе правила сохраняйте его относительный порядок и проверяйте итоговый
  CSS через сборку.
- Доменный класс сохраняйте при миграции на общий primitive (`btn-primary`,
  `dashboard-selection-icon` и т. п.). Удаляйте compatibility-классы только
  после перевода всех потребителей и обновления тестов.

## Доступность и адаптивность

- Интерактивное действие должно быть `button`, `a` или формовым элементом, а не
  кликабельным `div`. У icon-only кнопки всегда есть видимый или
  `aria-label`-текст.
- Для переключателей отражайте состояние через `aria-pressed`, для меню —
  через `aria-expanded` и подходящую роль, для модалки — `role="dialog"`,
  `aria-modal` и закрытие по Escape/наружному клику согласно контракту `UiModal`.
- Новая разметка должна работать с клавиатурой и touch. Не полагайтесь только
  на hover и не скрывайте единственный способ закрыть меню на телефоне.
- Breakpoint и media-query берите из существующего layout-контракта и
  проверяйте desktop и mobile сценарий для каждого нового dashboard-контрола.

## Тесты и проверка

- Новый primitive получает компонентный тест на props, события, disabled/loading,
  keyboard/focus и ARIA-контракт, если эти свойства ему принадлежат.
- Новый dashboard-срез сначала покрывается тестом, затем старая разметка
  удаляется. Селекторы поведения (`data-*`, роли, доступные имена) стабильнее
  CSS-классов и должны описывать пользовательский контракт.
- После изменения UI запускайте затронутые тесты, `npm run build` и полный
  `npm run test:unit -- --maxWorkers=2`. Предупреждение Vite о больших чанках
  само по себе не является ошибкой сборки.
- В одном срезе меняйте одну архитектурную границу: primitive, dashboard-секцию,
  CSS-модуль или composable. Если меняются две границы, добавьте в описание
  причины и отдельную проверку каждой.

## Документация и интеграция

- При изменении границ компонентов, CSS-модулей или порядка roadmap обновляйте
  `docs/redesign-plan-frox.md` и README соответствующего каталога.
- Каждый срез делайте в отдельной ветке и вливайте в `dev` только после build,
  затронутых тестов и полного unit-набора.
