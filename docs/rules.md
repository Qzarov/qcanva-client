## Общие правила

Этот раздел одинаков в трёх репо: `canvas-server-back`, `qcanva-client`, `qspace-agent`. Меняешь его в одном — поменяй дословно во всех трёх.

### Документация живёт вместе с кодом

- Документацию обновляешь **в том же PR (коммите), что и код**. PR, который меняет поведение, API или устройство кода без правки `docs/`, не готов.
- Что обновлять:
  - появилась, пропала или поменялась функция → `docs/features.md`;
  - изменился эндпоинт, команда CLI или протокол → API-документ репо;
  - новый модуль, новая связь между модулями или репо → архитектура репо; связь между репо → общая схема в хабе, [docs/architecture/system.md](https://github.com/Qzarov/canvas-server-back/blob/q-space/docs/architecture/system.md);
  - новое правило или найденная ловушка → `docs/rules.md` (общий раздел — во всех трёх репо).
- В шапке документа, который сверял с кодом, обнови строку «Сверено с …».
- Перед PR прогони `tools/docs-check <корень репо>` из папки проекта `/home/vlad/Code/suka_pizdec` (проверяет, что пути и `файл:строка` в документах существуют).
- В документах — только то, что подтверждено кодом. Номера строк быстро стареют: ссылайся на файл и имя символа, строки — только когда без них не найти.

### Задачи, статус и роадмап — в qcanva

- Трекинг задач, текущее состояние, роадмап, баги и идеи ведутся в qcanva (Q Space, https://canvas.qzarov.pro/dashboard, MCP `canvas`): статус-документ «Q Space: статус, задачи, идеи» `6e65d09d-245d-4a23-940d-6bb56b2b9721`, папка «Q Disk» `ff70f170-b9e5-4fd9-a6fb-0b41e42f7b24`.
- Не в `docs/`, не в GitHub issues и не в локальных файлах. `docs/` описывает, **как устроено и что уже есть**; qcanva — **что делаем, что сломано и что дальше**.
- После заметного шага (PR, решение feofan, найденная проблема) — строка в статус-документе.
- GitHub issues и комментарии массово не создавать.

### Ветки, коммиты, PR

- `canvas-server-back`, `qcanva-client`: работа идёт в интеграционную ветку `q-space`. PR — draft, прямо в `q-space`, от свежего `origin/q-space`. Не стеком (base = другая фича): мерж такого PR уходит в ветку-родителя, а не в `q-space`. Зависишь от несмерженной ветки — жди её мержа. `q-space` → `dev` вливает feofan; `dev` и `main` напрямую не трогать, PR не мержить.
- До выкатки 1.0 в `q-space` идут только фиксы релиза; PR, где меняется только документация, — можно.
- `qspace-agent`: PR нет, коммиты идут в `main`; пушить только после слова feofan.
- Коммиты и PR без трейлера `Co-Authored-By` и без названий моделей ИИ (в коде тоже). Тело PR кончается строкой `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
- Работай в своём worktree от нужной ревизии: рабочие копии в `/home/vlad/Code/suka_pizdec/*` часто стоят на чужих ветках или detached HEAD. Чужие ветки читай через `git show origin/<ветка>:<путь>` или отдельный worktree.

### Прод и секреты

- Прод не трогать: VPS, его `.env`, `data.sqlite`, Postgres Immich. По SSH туда не ходить, не деплоить.
- Секреты, токены, содержимое `.env` не печатать и не писать в документы (имена переменных — можно).

### Общий ноутбук

- Ноутбук делят несколько чатов, Docker стенда, Immich и сборки. Перед тяжёлым запуском (полный Jest, `cargo test --workspace`, release-сборка, `docker build`, Gradle, эмулятор) — `free -g`; если `available` меньше ~8 ГБ, не запускать.
- Jest — `--maxWorkers=2`, vitest — `--maxWorkers=2`, cargo — `-j 4`. Свои долгие процессы и worktree с `target/` после задачи не оставлять.
- `pkill -f` / `pgrep -f` по шаблону находят и сам скрипт, который их вызывает. Процессы ищи по PID или `pgrep -x <имя>`.
- `find` здесь — это bfs: для «изменено за N минут» используй `-mmin -N`, а не `-newermt '-N minutes'`.

### agy и другие агенты

- Делегирование в agy — по `~/.claude/CLAUDE.md`. agy не читает `CLAUDE.md`, `AGENTS.md` и этот файл: нужные правила вставляй прямо в промпт.
- В `-p` agy молча завершается на любой shell-команде, которой нет в разрешённых, — перечисляй в промпте точные команды, чтение и поиск — только его файловыми инструментами. Не проси его запускать `free` и фоновые команды.
- agy бывает уверенно рапортует об успехе, которого не было, и сдвигает номера строк: решающие факты из его отчёта подтверждай точечно (`git show`, `sed -n`, `grep`).

## Правила репо: qcanva-client

### Проверки — сам

- CI на PR не гоняет ни тесты, ни сборку (единственный workflow — `.github/workflows/android-release.yml`, по тегам `v*`). Перед PR прогоняешь сам:
  - `npm run test:unit -- --maxWorkers=2` — vitest (`vitest.config.ts`). Скрипта `npm test` нет.
  - `npm run build` — это `vue-tsc -b && vite build`, **единственная проверка типов**. Линтера нет.
  - Не запускай сборку и vitest одновременно — не хватает памяти.
- `npm run test:visual` — скриншотные тесты Playwright темы (`tests/theme.visual.spec.ts`), по необходимости.

### Код

- Состояние — модульные синглтоны и composables (`src/composables/`), Pinia нет. Не добавляй стор-библиотеку без решения feofan.
- i18n — один файл `src/composables/useI18n.ts`. Новый ключ добавляй **и в `ru`, и в `en`**.
- HTTP к хабу — только через `src/api/*`. Новый эндпоинт хаба → функция в `src/api/`, и строка в `docs/features.md`, если функция видна в интерфейсе (или в таблице «есть в API-слое, нет в интерфейсе»).
- `src/views/DashboardView.vue` — ~4,4 тыс. строк: целиком не читать, искать внутри и читать фрагменты.
- `postinstall` применяет `patch-package` (`patches/`): после `npm install` патчи должны примениться без ошибок.

### Окружение и стенд

- `.env.production` смотрит на прод-API. Для стенда и локальной сборки задавай `VITE_API_URL` и `VITE_CANONICAL_ORIGIN` явно.
- Вкладка «Фото» — за флагом `VITE_PHOTOS_ENABLED=1`; мок данных — `VITE_PHOTOS_MOCK=1`.
- Веб на стенде собирается из своего worktree: `CLIENT_DIR=../../../<wt-клиента> docker compose build web` в `canvas-server-back/deploy/staging`.
- Android (Capacitor): `npm run android:build:debug` и др. — Gradle тяжёлый, сначала `free -g`; эмулятор — только с `hw.ramSize=2048`, гасить сразу после проверки (`adb emu kill`).

### Worktree

- `node_modules` — симлинк на `node_modules` основного клона (`ln -s ../qcanva-client/node_modules node_modules`). Файлы внутри `node_modules` не правь.

- [ ] `npm run build` — без ошибок.
- [ ] `docs/` обновлены (или в PR сказано, почему не нужно), `tools/docs-check .` — OK.
