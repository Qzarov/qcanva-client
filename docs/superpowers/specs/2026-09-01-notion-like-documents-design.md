# ТЗ: Notion-подобные документы в QCanva

Дата: 2026-09-01
Затрагивает репозитории: `canvas-server-front`, `canvas-server-back`

## 1. Цель

Довести текстовые документы QCanva до уровня, на котором ими можно вести базу
знаний: богатый набор блоков, быстрый ввод без мыши, связи между страницами.

Ключевое ограничение, заданное заказчиком: **приложение не должно тормозить**.
Производительность здесь не пожелание, а проверяемое требование с числом и
бенчмарком (раздел 9).

## 2. Что сломано сегодня

Перед проектированием состояние проверено запуском кода, не чтением.

Серверная проекция документа (`text-document-projection.ts`) — самописная
**закрытая схема из трёх типов**: параграф, заголовок, картинка. Всё остальное
она уничтожает:

| Что в документе | Что видит сервер |
| --- | --- |
| Маркированный / нумерованный список | `<p></p>`, текст потерян |
| Чек-лист | `<p></p>`, текст потерян |
| Блок кода | `<p></p>`, текст потерян |
| Таблица | `<p></p>`, текст потерян |
| Разделитель | `<p></p>` |
| Цитата | схлопывается в обычный параграф |

При этом **списки и чек-листы в редакторе уже есть** — кнопки «List» и «Tasks»
в тулбаре работают. Последствия для живых документов:

- содержимое **не теряется**: Yjs-состояние хранит структуру честно
  (проверено — `<bulletlist><listitem>…` на месте);
- но всё производное видит мусор. Список из двух пунктов даёт
  `<p>first itemsecond item</p>` — пункты склеены **без разделителя**;
- значит документ с чек-листом **не находится поиском** по его содержимому и
  показывается на канвасе как «Пустой документ»;
- при импорте из HTML списки теряются безвозвратно, ещё на входе.

Любой новый блок, добавленный поверх этой схемы, унаследует ровно эту
невидимость. **Замена схемы — фундамент, а не пункт списка фич.**

## 3. Границы работы

Делаем:

- замену схемы проекции и перенос её с горячего пути;
- новые блоки: цитата, разделитель, callout, код с подсветкой;
- сворачиваемые заголовки и блок содержания;
- slash-меню, markdown-ввод, перетаскивание блоков, панель над выделением;
- @-упоминания страниц, создание страницы из упоминания, обратные ссылки;
- ограничение ёмкости документа и переход в новую страницу при переполнении;
- пересчёт производных данных у существующих документов.

Не делаем:

- **иерархию страниц.** Дерево в продукте одно — папки. Страницы связываются
  ссылками, а не вложенностью. Это снимает проблему двух конкурирующих
  иерархий и вопрос «что делать с подстраницами при перемещении родителя»;
- базы данных, представления, фильтры;
- комментарии к блокам;
- изменения в HTML-документах: они остаются как есть;
- упоминания из канваса и HTML-доков — только между текстовыми документами.

## 4. Архитектура: схема и проекция

### 4.1 Один источник правды для схемы

Сервер получает Yjs-фрагмент, через `y-prosemirror` превращает его в
ProseMirror-JSON и рендерит `html` / `plainText` по **той же схеме узлов**, что
использует редактор. Самописный разбор удаляется целиком.

Рассмотренная альтернатива — дописывать самописную проекцию под каждый новый
блок — отвергнута: это механизм, который и привёл к текущей поломке. Каждый
блок пришлось бы реализовывать дважды, а расхождение проявляется не падением, а
тихой пропажей пользовательского контента.

Вариант «считать производные на клиенте и присылать на сервер» отвергнут:
поиск и превью стали бы зависеть от честности клиента, документы из MCP и
HTML-импорта остались бы без производных, а при совместном редактировании
возникла бы гонка «кто последний прислал».

### 4.2 Как разделить схему между двумя репозиториями

Фронт и бэк — **отдельные репозитории**, монорепы нет, поэтому общий модуль в
буквальном смысле невозможен. Публиковать npm-пакет для проекта такого размера
избыточно.

Решение: **дублировать один небольшой файл описания узлов** в обоих
репозиториях и подпереть его **контрактным тестом**. Обе стороны вычисляют
отпечаток схемы (имена узлов, их атрибуты, допустимая вложенность) и сверяют с
зафиксированной в коде константой. Добавили узел на клиенте и забыли про
сервер — падает тест, а не пользовательский контент.

Без этого теста вся конструкция держится на дисциплине, а дисциплина уже один
раз не сработала.

### 4.3 Проекция уходит с горячего пути

Сейчас `projectYjsState` вызывается **на каждом апдейте** — то есть на каждой
пачке нажатий — и делает полный разбор всего документа
(`text-documents.service.ts`, приём апдейта).

Новый порядок:

- приём апдейта делает только необходимое для корректности: применяет
  Yjs-апдейт и сохраняет его в журнал;
- пересчёт `html` / `plainText`, индекса ссылок и счётчика блоков —
  **отложенно**: по дебаунсу после затишья правок и на границах снапшотов.

Производные данные обслуживают поиск, превью ноды на канвасе и экспорт. Ни
одному из них не нужна точность до миллисекунды. Плата — отставание поиска и
превью на несколько секунд; размен сознательный.

Побочный выигрыш: сегодняшний редактор тоже станет быстрее, а тяжёлый документ
перестанет подъедать отзывчивость соседних канвасов (процесс однопоточный и
общий).

## 5. Модель данных

Формат хранения не меняется: Yjs-состояние, журнал апдейтов, снапшоты.
Добавляется:

- **Индекс ссылок** — таблица связей «документ → документ» (источник, цель,
  время обновления). Переписывается вместе с проекцией: разобрали документ —
  обновили его исходящие ссылки. Ссылки берутся из узлов ProseMirror, отдельный
  разбор текста не нужен.
- **Счётчик блоков верхнего уровня** — хранится рядом с проекцией, чтобы
  клиент и сервер судили о ёмкости по одному значению.

Обратные ссылки читаются обратным запросом по цели.

## 6. Редактор: блоки и ввод

### 6.1 Новые блоки

- **Цитата** и **разделитель** — есть в StarterKit, включить и научить проекцию.
- **Callout** — собственный узел: вариант (`info` / `warning` / `success` /
  `danger`), иконка по варианту, внутри произвольные блоки.
- **Блок кода с подсветкой** — `CodeBlockLowlight` с выбором языка.

Иконки callout — **Lucide, не эмодзи**. Пакет Lucide в проекте не установлен;
иконки вклеиваются inline-SVG в стиле Lucide (24×24, stroke-width 2), как это
уже сделано в остальном коде. Callout следует этой же практике.

Подсветка кода берёт **фиксированный набор языков**: js/ts, python, bash, json,
sql, html, css. Полный набор `lowlight` — сотни килобайт в бандл, а чанк
документа уже 460 КБ. Расширять набор — только осознанно, по требованию.

### 6.2 Сворачиваемые заголовки

Сворачивать можно **каждый** заголовок; при открытии документа всё развёрнуто.
Готового расширения в TipTap нет — это плагин ProseMirror, который прячет узлы
после заголовка до следующего заголовка того же или более высокого уровня.
Самая кастомная часть работы.

Два решения фиксируются явно:

- **состояние сворачивания не попадает в документ**, оно локальное у каждого
  читателя (`localStorage`). Иначе один человек свернул раздел — и раздел
  схлопнулся у всех, кто сейчас в документе;
- **свёрнутое содержимое остаётся в проекции**: индексируется поиском и
  попадает в экспорт. Сворачивание — способ смотреть, а не способ хранить.

### 6.3 Блок содержания

Узел без собственного содержимого. Список заголовков строится на лету из
документа и обновляется вместе с ним; клик — прокрутка к заголовку.

В производном `html` рендерится как оглавление (полезно для экспорта), в
`plainText` **пропускается** — иначе заголовки попадут в поисковый индекс
дважды и перекосят релевантность.

### 6.4 Ввод

- **Slash-меню** по `/` с поиском по блокам.
- **Markdown-ввод**: `## `, `- `, `> `, ```` ``` ````. В TipTap большая часть
  работает из коробки.
- **Перетаскивание блоков** — ручка слева от блока.
- **Панель форматирования над выделением.**

Существующий верхний тулбар остаётся: slash-меню и панель над выделением его
дополняют, а не заменяют.

## 7. Упоминания, создание страниц, обратные ссылки

### 7.1 Вставка и создание

Расширение Mention (TipTap, свободное). Триггер `@` — поиск по заголовкам
страниц, внизу списка всегда пункт **«Создать страницу "…"»** с набранным
текстом.

Создание кладёт новый текстовый документ **соседом в ту же папку**, что и
текущий, вставляет упоминание и переводит фокус в новую страницу.

### 7.2 Что хранит упоминание

Идентификатор документа плюс заголовок на момент вставки. Отображается
**актуальный** заголовок, подтянутый по идентификатору; сохранённый — запасной
вариант. Иначе переименование страницы оставит по всем документам устаревшие
подписи.

### 7.3 Права: сознательное решение

**Заголовки недоступных документов показываются** — и в упоминаниях, и в
обратных ссылках. Тела документов остаются закрытыми; раскрытие ограничено
названием.

Это осознанное решение заказчика, принятое после разбора последствий. Отдельно
зафиксировано неочевидное следствие: **обратные ссылки раскрывают заголовок
шире, чем упоминания**. Приватный документ, сославшийся на общедоступную
страницу, покажет своё название всем, кто эту страницу видит — то есть автор
приватного документа светит его название кругу читателей цели.

При клике на недоступную страницу открывается **существующее окно запроса
доступа** (сущность `access_request`, API `accessRequests`, тот же механизм, что
на экране документа): название страницы, владелец, выбор роли (просмотр /
редактирование), кнопка запроса. Владельцу запрос попадает в уже существующий
список входящих.

Удалённый документ: упоминание становится неактивным текстом, а не битой
ссылкой.

### 7.4 Обратные ссылки

Блок в конце страницы «Ссылаются на эту страницу» — список документов-
источников по индексу ссылок. Недоступные источники показываются заголовком,
клик открывает то же окно запроса доступа.

Индекс обновляется вместе с проекцией, отложенно: свежепоставленная ссылка
появится в бэклинках цели через несколько секунд.

## 8. Ёмкость документа

**Лимит — 200 блоков верхнего уровня.** Список любой длины, callout с
несколькими абзацами, блок кода — каждый считается за один. Правило действует
только на текстовые документы.

**Предупреждение на 180 блоках** (0.9 от лимита): ненавязчивая плашка о том,
что ёмкость заканчивается.

**На 200 блокируется ровно одно действие — вставка нового блока верхнего
уровня.** Правка текста, форматирование, удаление, работа внутри существующих
блоков доступны всегда: упереться в лимит не должно означать «документ
заморожен».

Вместо заблокированной вставки — плашка **«Продолжить в новой странице»**.
Нажатие переиспользует механику раздела 7: создаётся страница соседом в той же
папке, в конец текущей вставляется упоминание, курсор переезжает туда. Обратная
ссылка появляется автоматически. **Содержимое никуда не переносится.**

Рассмотренная альтернатива — автоматически разрезать документ при переполнении
— отвергнута как небезопасная: в CRDT нельзя честно отклонить смёржившееся
состояние, перенос блоков между двумя Yjs-документами не атомарен (удаление и
вставка — разные транзакции, конкурентная правка теряется или дублируется),
undo работает в пределах одного документа и разрез не отменяет.

**Вставка из буфера, которая не влезает**: вставляем то, что помещается, и
сообщаем, сколько не поместилось. Отклонять всю вставку целиком — значит молча
потерять работу человека.

**Совместное редактирование.** Двое одновременно добавили блоки — документ
может оказаться на 205. Правило жёсткое: **блоки никогда не удаляются ради
соблюдения лимита.** Превышение фиксируется, плашка показывается, дальнейшая
вставка блокируется, пока не вернулись под лимит.

Считает блоки клиент по своему состоянию документа (число детей верхнего
уровня, дёшево). Серверное значение нужно для наблюдаемости и согласованности с
поиском и превью.

## 9. Производительность: бюджет

Замеры текущего состояния (применение апдейта вместе с проекцией, то есть то,
что происходит на каждой пачке нажатий):

| Размер документа | Yjs-состояние | Время |
| --- | --- | --- |
| 50 абзацев | 11 КБ | ~1.6 мс |
| 200 абзацев | 44 КБ | ~4.8 мс |
| 800 абзацев | 178 КБ | ~19 мс |

Скорость набора текста от смены схемы не зависит: нажатия рисует ProseMirror
локально, сервер подтверждает асинхронно. Меняется стоимость серверной
обработки, и она уже сейчас O(размер документа) на каждую пачку нажатий, на
однопоточном процессе, который держит всю БД в памяти и обслуживает вебсокеты
канваса.

**Требование:** после переноса проекции с горячего пути приём апдейта на
документе в 200 блоков укладывается в **~2 мс**.

Проверяется **бенчмарком в составе тестов**, а не замером руками. Без этого
«не тормозит» через полгода тихо перестанет быть правдой.

## 10. Миграция

Yjs-состояние — источник правды — не трогаем. Портятся только производные,
поэтому миграция это **разовый пересчёт производных** по сохранённым
состояниям: `html`, `plainText`, индекс ссылок, счётчик блоков. Операция
идемпотентная, можно повторять.

**Ограничение, нарушение которого стоит данных.** Прод-БД — sql.js: вся база
живёт в памяти процесса и сбрасывается на диск целиком. Любой внешний писатель,
пока приложение живо, будет затёрт ближайшим сбросом. Пересчёт обязан
выполняться **внутри процесса приложения** (разовая админ-ручка или задача при
старте), а не скриптом по `data.sqlite` сбоку.

Объём: на проде **5 текстовых документов**. Минуты, окно обслуживания не нужно.

**Что не восстановится.** Документы, импортированные из HTML, потеряли списки
ещё на входе — их нет и в самом Yjs-состоянии. Пересчёт восстановит структуру
только там, где она сохранилась, то есть у набранного в редакторе.

## 11. Тестирование

- **Контрактный тест отпечатка схемы** в обоих репозиториях — предохранитель от
  расхождения клиента и сервера.
- **Круговой прогон по каждому типу блока**: документ из редактора → проекция →
  `html` / `plainText`. Именно того, чего сейчас нет, и из-за чего списки тихо
  пропадали. Расширяется существующий `text-document-projection.spec.ts`.
- **Бенчмарк как тест**: применение апдейта на 200 блоках укладывается в бюджет
  раздела 9.
- **Права**: заголовок недоступного документа виден, тело — нет; окно запроса
  доступа открывается; обратные ссылки показывают недоступные источники
  заголовком.
- **Ёмкость**: вставка блокируется на 200, предупреждение на 180, вставка из
  буфера обрезается с уведомлением, слияние с превышением ничего не удаляет.
- **Локализация**: новые подписи заведены на оба языка (`ru`, `en`), меню не
  содержит текста другой локали.

Ключевые инварианты проверяются **мутацией** — код намеренно ломается, тест
обязан упасть. Проверяются как минимум: пропажа блока в проекции, утечка тела
недоступного документа, удаление блоков при переполнении. На этом проекте
мутационная проверка уже дважды ловила тесты, проходившие при сломанной логике.

## 12. Риски

1. **Лицензия на перетаскивание блоков.** Официальное расширение drag-handle у
   TipTap относится к платному тиру. У нас v2; для него есть свободная
   альтернатива (`tiptap-extension-global-drag-handle`, MIT). Лицензию и
   совместимость надо проверить **первым шагом**: если свободный вариант не
   подойдёт, перетаскивание придётся писать самим либо покупать лицензию.
2. **Рендер HTML на сервере.** Подход требует `prosemirror-model` и
   `y-prosemirror` на бэке (сейчас там из релевантного только `yjs`). Чем
   рендерить HTML — `@tiptap/html` тянет DOM-прослойку. Снять этот вопрос надо
   до начала основной работы; запасной вариант — собственный сериализатор по
   ProseMirror-JSON, схема узлов при этом всё равно остаётся общей.
3. **Размер бандла.** Подсветка кода и новые расширения увеличат чанк
   документа, который уже 460 КБ. Фиксированный набор языков — часть смягчения;
   после реализации размер надо перемерить.
4. **Расхождение схем между репозиториями** — смягчается контрактным тестом
   (4.2), но остаётся структурным риском разделённых репозиториев.

## 13. Порядок работ

1. **Снять риски 1 и 2** — проверить лицензию drag-handle и способ рендера HTML
   на сервере. До этого основную работу не начинать.
2. **Фундамент**: общая схема, контрактный тест, замена проекции, перенос её с
   горячего пути, бенчмарк бюджета.
3. **Миграция** производных у существующих документов.
4. **Блоки**: цитата, разделитель, callout, код с подсветкой.
5. **Заголовки и содержание**: сворачивание, блок оглавления.
6. **Ввод**: slash-меню, markdown, панель над выделением, перетаскивание.
7. **Связи**: упоминания, создание страницы, обратные ссылки, окно запроса
   доступа.
8. **Ёмкость**: счётчик, предупреждение, блокировка вставки, продолжение в
   новой странице.

Пункты 2 и 3 обязаны идти первыми: без них любой новый блок наследует текущую
невидимость.

Объём работы больше одного плана реализации. Естественное деление: пункты 1–3
(снятие рисков, фундамент, миграция) — первый план, он самостоятельно ценен, так
как чинит пропажу списков из поиска и превью. Пункты 4–8 — второй план, они
опираются на готовый фундамент и между собой слабо связаны, порядок внутри можно
менять по приоритету.
